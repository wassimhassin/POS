# Architecture decision log

Short records: context → decision → consequences. A change to a decision needs a new entry that supersedes it.
Details and rationale: [10-PRODUCTION-FOUNDATION.md](10-PRODUCTION-FOUNDATION.md).

| ID | Date | Decision | Status |
|---|---|---|---|
| ADR-001 | 2026-11-19 | **Organization → Business → Branch.** The organization is the tenant and billing party (`tenant_id` in docs 01–03 ≡ `organization_id`). The business owns legal/fiscal identity, catalog and taxes. The branch is a site with exactly one active gateway. | Accepted |
| ADR-002 | 2026-11-19 | **Cloud = one modular monolith (`Pos.Cloud`)** with modules as folders/namespaces, per-module endpoints and entity configuration, and no cross-module table access. A module moves to its own project only when justified. No microservices, broker or Redis without measured need. | Accepted |
| ADR-003 | 2026-11-19 | **Isolation:** the scope comes from the authenticated principal; composite tenant keys on every owned row; out of scope → 404; mandatory cross-tenant tests; **PostgreSQL RLS** on the app role as defence in depth (from 2.1). Platform admin uses a separate role/scheme, audited. | Accepted |
| ADR-004 | 2026-11-19 | **Two authorities, one writer each.** The cloud is authoritative for *configuration* (catalog, prices, staff, permissions, entitlements) and delivers it as versioned branch snapshots pulled by the gateway over its existing signed credential. The gateway is authoritative for *branch operations* (orders, tables, payments, cash, stock movements) and sends them through the existing outbox. The gateway stops being catalog authority; the cloud never edits active branch state. | Accepted |
| ADR-005 | 2026-11-19 | **Reuse the gateway command engine** (operation id, expected version, replay/resolve, serialized writer, SignalR notify + snapshot) for every new branch command. Reuse the outbox sync for every new event type. | Accepted |
| ADR-006 | 2026-11-19 | **Identity:** ASP.NET Core Identity in the cloud for owners/managers (cookie + MFA). POS/waiter staff sign in with a PIN verified by the gateway against hashed credentials in the snapshot; device trust (existing keys) stays separate from staff identity. | Accepted |
| ADR-007 | 2026-11-19 | **API conventions** (doc 10 §5): `/v1`, error envelope `{code, message, current?}`, operation ids, optimistic versions, cursor paging, minor-unit money, UTC + branch timezone, OpenAPI from the first-party package for the cloud. | Accepted |
| ADR-008 | 2026-11-19 | **Frontends:** one Vite app per surface (dashboard, POS, waiter, KDS, QR, admin) with npm workspaces and shared `packages/ui` (semantic tokens, open for Claude Design) and `packages/contracts`. No component library before design approval. | Accepted |
| ADR-009 | — | **LAN TLS trust for browser clients** (waiter, KDS). | **Open**, needed before 2.7/2.8 |
| ADR-010 | 2026-11-19 | **Migrations:** EF expand → migrate → contract, run as an explicit deploy step with the owner role; SQLite forward-only with a verified gateway backup before migrating; upgrade order cloud → gateway → terminals; the cloud accepts sync schema N and N-1. | Accepted |
| ADR-011 | 2026-11-19 | **Configuration:** code defaults + environment variables only, secrets from the hosting secret store; fault injection compiled out of Release; separate keys/certificates per environment. | Accepted |
| ADR-012 | — | **Cloud hosting region, data residency, RPO/RTO.** | **Open**, needs legal input |
| ADR-013 | 2026-11-19 | **Frozen wire shapes for gateways.** The error envelope is exactly `{code, message}`, framework errors included. Gateways deserialize cloud responses strictly, so adding a member to any response they read is breaking: use new codes or headers, or `/v2`. OpenAPI schemas declare `additionalProperties: false`. | Accepted |
| ADR-014 | 2026-11-19 | **OpenAPI as a reviewed artifact.** Generated by the first-party package, committed at `docs/api/cloud-v1.openapi.json`, drift-checked by a test. The live endpoint is opt-in (`run --openapi`). No servers, examples or internal types. | Accepted |
| ADR-015 | 2026-11-19 | **Cloud user sessions are server-side.** Opaque random cookie `__Host-pos_session` (Secure, HttpOnly, SameSite=Strict), SHA-256 stored in `user_sessions`, checked on every request: idle 2 h, absolute 12 h, hourly key rotation with 1-minute grace, security-stamp binding, immediate revocation. Every credential or privilege change starts a new session. No JWTs, no Identity cookie handler, no Data Protection key ring. Refines ADR-006 (doc 12). | Accepted |
| ADR-016 | 2026-11-19 | **Account emails carry single-use hashed tokens** (`auth_tokens`: purpose, expiry, atomic consumption) in the URL fragment. Anonymous account endpoints never reveal whether an address has an account. Mail goes through `IAuthMailer` (pickup directory now, provider adapter later). | Accepted |
| ADR-017 | 2026-11-19 | **MFA = TOTP (RFC 6238) + 10 hashed recovery codes**, with replay protection by last accepted step and a lockout counter shared with passwords and reset only by a complete sign-in. Mandatory for privileged users (any live organization membership): privileged users without MFA are confined to enrolment. WebAuthn later. | Accepted |
| ADR-018 | 2026-11-19 | **Owner onboarding is invitation-only.** No public organization or privileged account creation. The platform operator issues a 72-hour single-use invitation by CLI (`owner-invite`, mailed only). Acceptance requires the same verified address and enabled MFA and creates an `owner` membership. Memberships grant no permissions until RBAC (2.1C). | Accepted |
| ADR-019 | 2026-11-19 | **Provisioning and enrollment are replayable for the same identity.** The gateway keeps one key per provisioning code (DPAPI, `cloud_link.pending_private_key`) and the terminal keeps its persisted key. A consumed code is accepted again only from the key that consumed it, with proof of possession, for an unrevoked credential, within 7 days (cloud) or 24 h (gateway), and the original result is returned without any write. Any other identity gets `invalid_code`. Enrollment retries transport failures 3 × 15 s. Wire shapes unchanged (doc 13 §1–2). | Accepted |
| ADR-020 | 2026-11-19 | **Application secrets at rest use AES-256-GCM data keys** from `POS_CLOUD_DATA_KEYS`: the first key is active, the others decrypt only, and the associated data binds the purpose and the owner id. A key id is stored per row and null marks legacy plaintext, migrated lazily on use and in bulk by `mfa-rekey`. `check-config` errors on rows under unknown keys. KMS/HSM envelope later (doc 13 §3). | Accepted |
| ADR-021 | 2026-11-19 | **Security mails are queued in memory and sent by one background dispatcher** through exactly one `IMailTransport`: a pickup directory (dev) or SMTP with STARTTLS (plain SMTP only to loopback). Transient failures are retried with exponential backoff, 5 attempts; permanent failures are not. Logs never contain recipients, bodies or credentials. No durable outbox, so live links are never stored: the user or operator repeats the flow after a crash. Supersedes the transport part of ADR-016 (doc 13 §4). | Accepted |
| ADR-022 | 2026-11-19 | **Retention:** ended sessions 30 days, expired tokens 7 days, unconfirmed MFA setups 1 day. Deleted by the runtime role in bounded batches, hourly and via `cleanup`. The security audit is kept at least 365 days (default 400) and is pruned only by `audit-prune` with the owner role; the runtime role stays append-only (doc 13 §5). | Accepted |
| ADR-023 | 2026-11-20 | **Cloud RBAC = one membership per (organization, user) with one role and one scope** (organization, business or branch, as for report keys), kept inside the organization by composite foreign keys. Roles Owner > Admin > Manager > Viewer map to a permission catalog in code (`organization.read`, `members.read`, `members.invite`, `members.manage`). Owners and admins are organization-wide. Refines ADR-006 for cloud users; gateway, device, report-key and offline staff authorization are unchanged (doc 14). | Accepted |
| ADR-024 | 2026-11-20 | **Deny by default, evaluated per request.** Organization routes take the organization from the path and the access from the caller's membership row, read on every request (no claims or caches). Not a member → 404, missing or undeclared permission → 403. Roles are granted, changed or revoked only by a strictly higher role (owners: any), inside the actor's scope, re-checked under the organization lock. | Accepted |
| ADR-025 | 2026-11-20 | **Membership changes are serialized per organization** (`FOR NO KEY UPDATE` on the organization row) and versioned (`expectedVersion`). The last active owner cannot be demoted or revoked. Every change revokes all sessions of the affected user and renews their security stamp. | Accepted |
| ADR-026 | 2026-11-20 | **Invitations are hashed, single-use, 72-hour links** for one address. Acceptance requires the same verified address and enabled MFA, and the inviter must still hold the authority to grant that role and scope. A newer invitation supersedes an older one. Owner onboarding by CLI (ADR-018) is unchanged. Access changes are audited with actor, target and ids only. | Accepted |
