# 16 — Cloud structure management: organization → business → branch (Phase 2.1F)

Scope: versioned cloud APIs for the organization, its businesses and their branches, so routine administration no longer
needs the platform CLI. The phase reuses Identity (doc 12), roles and scopes (doc 14), row-level security (doc 15) and
the security log. It also hardens the platform side:
- a dedicated least-privilege platform role;
- an audited gateway listing;
- narrower pre-tenant lookups.

The phase does not add a catalog, inventory, subscriptions or POS UI, and makes no wire change to existing endpoints. All
additions are new routes and new permission codes. Decisions: ADR-031…034.

---

## 1. Permissions and roles

Three codes are added to the doc 14 catalog:

| Code | Grants |
|---|---|
| `organization.manage` | Rename the organization |
| `businesses.manage` | Create businesses (requires an organization-wide scope) and rename businesses inside one's scope |
| `branches.manage` | Create branches in a business covered by one's scope, and rename branches inside one's scope |

| Role | Permissions (2.1F additions in bold) | Typical use |
|---|---|---|
| Owner | all, including **`organization.manage`**, **`businesses.manage`**, **`branches.manage`** | Everything |
| Admin | all except `organization.manage` | Structure below the organization |
| Manager | `organization.read`, `members.read`, **`branches.manage`** | A business manager creates and renames its branches; a branch manager renames its own branch |
| Viewer | `organization.read` | Read only |

A permission is never enough on its own: every operation also checks the member's **scope**.

| Operation | Permission | Scope needed |
|---|---|---|
| Read organization | `organization.read` | any (it is the member's organization) |
| Rename organization | `organization.manage` | organization (owners are always organization-wide) |
| List or read businesses | `organization.read` | the business is inside the scope |
| Create business | `businesses.manage` | organization-wide |
| Rename business | `businesses.manage` | covers the business |
| List or read branches | `organization.read` | the branch is inside the scope |
| Create branch | `branches.manage` | covers the whole business (organization- or business-scoped) |
| Rename branch | `branches.manage` | covers the branch |

**No escalation path.** The API never changes roles, scopes or the parent of a resource. Member management stays with
doc 14's rank rules. A manager cannot gain `businesses.manage` by creating something, and a branch manager cannot create
a sibling branch.

## 2. API (session cookie, full session with MFA where required; deny-by-default organization filter)

| Method and path | Permission | Request → response |
|---|---|---|
| `GET /v1/organizations/{org}` | `organization.read` | → `{id, name, version, createdAt, updatedAt}` |
| `PATCH /v1/organizations/{org}` | `organization.manage` | `{name, expectedVersion}` → organization |
| `GET /v1/organizations/{org}/businesses` | `organization.read` | → businesses in scope `[{id, name, version, createdAt, updatedAt}]` |
| `POST /v1/organizations/{org}/businesses` | `businesses.manage` | `{name}` → **201** business |
| `GET /v1/organizations/{org}/businesses/{business}` | `organization.read` | → business |
| `PATCH /v1/organizations/{org}/businesses/{business}` | `businesses.manage` | `{name, expectedVersion}` → business |
| `GET /v1/organizations/{org}/businesses/{business}/branches` | `organization.read` | → branches of that business in scope `[{id, businessId, name, version, createdAt, updatedAt}]` |
| `POST /v1/organizations/{org}/businesses/{business}/branches` | `branches.manage` | `{name}` → **201** branch |
| `GET /v1/organizations/{org}/branches/{branch}` | `organization.read` | → branch |
| `PATCH /v1/organizations/{org}/branches/{branch}` | `branches.manage` | `{name, expectedVersion}` → branch |

The existing `GET /v1/organizations/{org}/branches` (doc 14) is unchanged.

**Identifiers and immutable fields.**
- Ids are generated by the server (UUIDv7). A request body never carries an id, an organization or a parent.
- The JSON reader is strict, so an unknown field such as `id`, `organizationId` or `businessId` is a 400.
- Only `name` can change. Moving a branch to another business, or a business to another organization, is not
  supported.
- The CLI keeps `branch-create --id` for gateways initialized with their own branch id (doc 07).

**Validation.**
- Names are trimmed, contain 1–120 characters and no control characters (400 `invalid_name`).
- Names are unique among siblings, **ignoring case**: businesses within the organization, branches within their
  business (409 `name_taken`).
  - The comparison is done by the service (ordinal, culture-independent), not by the database, whose case folding
    depends on its locale.
  - Names are only unique within one organization, so a name used in another organization is always free.
- Limits: 100 businesses and 500 branches per organization (409 `limit_reached`).

**Errors are predictable and reveal nothing across tenants.**

| Situation | Answer |
|---|---|
| Not signed in, or the session was ended while the request was in flight (e.g. a concurrent role change) | 401 |
| Not a member of `{org}` (including another tenant's organization) | 404 `not_found`, the same body as a random id |
| A business or branch outside one's scope, or of another organization | 404 `not_found`, the same body as a random id (tested byte for byte) |
| A visible resource, but the role or scope does not allow the change | 403 `forbidden` (audited `permission_denied`) |
| Stale `expectedVersion` | 409 `version_conflict` |
| Duplicate name, limit reached | 409 `name_taken`, `limit_reached` |

## 3. Concurrency

- Every row carries a `version` (starting at 1) and an `updated_at`. A rename is a conditional update
  (`… WHERE version = expectedVersion`) that increments the version; if no row matched, the answer is
  `version_conflict`.
- Creations and renames of one organization take a `FOR NO KEY UPDATE` lock on its organization row, inside the same
  tenant transaction, before checking names and limits. Two concurrent requests for the same name therefore cannot both
  succeed.
  - The lock does not block gateway sync, which takes no lock on the organization row.
- Tests run eight concurrent renames with the same version (one wins), eight concurrent creations of the same name in
  mixed case (one wins), two siblings renamed to the same name at once (one wins), and six distinct creations in
  parallel (all succeed).

## 4. Tenancy, RLS and the platform role

- **Tenant context.** Every operation runs inside `BeginTenantAsync` or `InTenantAsync` of the caller's verified
  organization (doc 15). Writes therefore pass the `WITH CHECK` of the RLS policies, and reads see that organization
  only. The organization id in the path is used only after the session's membership there has been verified.
- **Foreign keys.** Composite foreign keys still bind branch → business → organization, so even a coding error could
  not attach a branch to another tenant's business.
- **Branches created by the API** get the same rows as `branch-create`: the branch plus its `branch_sync_states`
  checkpoint. The platform can then issue a gateway code for it, and the gateway registers and syncs (tested).

### Dedicated platform role (`POS_CLOUD_ADMIN_DB`, now required)

- Platform commands (`org-create`, `business-create`, `branch-create`, `gateway-code`, `gateways`, `gateway-revoke`,
  `report-key`, `owner-invite`) no longer fall back to the schema owner.
- The commands verify all of the following and refuse otherwise:
  - a user different from those of `POS_CLOUD_DB` and `POS_CLOUD_MIGRATION_DB`;
  - BYPASSRLS, because platform commands address any organization by id;
  - not superuser, CREATEROLE, CREATEDB or REPLICATION;
  - no ownership of, or CREATE on, the schema;
  - **exactly** these table privileges (any extra privilege is refused, any missing one is reported):

| Table | Privileges |
|---|---|
| `organizations`, `businesses`, `branches` | SELECT, INSERT |
| `gateway_credentials` | SELECT, UPDATE (revocation) |
| `branch_sync_states`, `provisioning_codes`, `report_keys`, `auth_tokens`, `auth_audit_events` | INSERT |
| `__EFMigrationsHistory` | SELECT |
| functions `app_enter_tenant(uuid)`, `app_current_organization()` | EXECUTE |

The role therefore cannot:
- read sales, sync events, memberships, users, sessions or the security log;
- delete or truncate anything;
- rewrite audit rows;
- change the schema.

`check-config` runs the same verification when `POS_CLOUD_ADMIN_DB` is set and prints `platform_role=ok`, `invalid` or
`not_configured`.

**Setup (once, by a superuser), then after every migration (by the schema owner):**

```sql
CREATE ROLE pos_platform LOGIN PASSWORD '…' BYPASSRLS NOSUPERUSER NOCREATEDB NOCREATEROLE;   -- once
GRANT CONNECT ON DATABASE pos_cloud TO pos_platform;                                         -- once
```
```powershell
& $cloud platform-grants --role pos_platform | & psql -v ON_ERROR_STOP=1 "<schema owner connection>"
```

`platform-grants` prints the exact `GRANT` statements; it is the single source used by deployments, the test kit and
the E2E harness. If a role created with older, broader grants is reused, run `REVOKE ALL ON ALL TABLES IN SCHEMA public
FROM pos_platform;` first. `check-config` names any excess privilege.

### Gateway listing is audited

`gateways [--branch <id>]` writes one `platform_gateways_listed` row **per organization whose gateways were listed**,
with details `branch=<id>|*;count=<n>`. When a branch has no gateway, its organization is still recorded with
`count=0`.

## 5. Narrower pre-tenant lookups (SECURITY DEFINER)

Migration `CloudStructureManagement` replaces the two widest lookups of doc 15:

| Before (2.1E) | After (2.1F) |
|---|---|
| `app_report_key(id)` returned the key's scope **and its stored SHA-256 secret hash** for any id | `app_report_key(id, secret_sha256)` returns the scope only for an **active key whose hash matches**; it never returns the hash |
| `app_user_memberships(user)` listed **any user's** memberships and organization names | `app_session_memberships(session, user)` returns memberships only if `session` is a **live (not revoked) session of that user**; organization names are no longer returned |

Session ids are server-generated, and only their own user sees them (in the session list; the cookie carries a separate
secret token). A user's own session id only reveals that user's own memberships, and an attacker with SQL access as
`pos_app` needs a live session id of the target user to enumerate that user's memberships. The remaining lookups (gateway
credential by id, provisioning code and invitation by secret hash, key-fingerprint existence, expired-invitation purge)
are unchanged: each already requires a secret, or returns only a public key or a yes/no answer.

The migration is reversible: its `Down` restores the 2.1E functions and drops the new columns. After applying it, run
the runtime grant `GRANT EXECUTE ON ALL FUNCTIONS IN SCHEMA public TO pos_app` again, then `platform-grants`.

## 6. Audit (ids and versions only, never names)

| Event | Details |
|---|---|

| `business_created` / `business_updated` | `business=…` / `business=…;version=n` |
| `branch_created` / `branch_updated` | `branch=…;business=…` / `branch=…;version=n` |
| `permission_denied` | `permission=…` (now for **every** refused write permission, not only member management), or the refused scope operation |

## 8. Limitations and residual risks (honest)

1. **No delete or archive** for businesses and branches. A mistaken branch stays, and can only be renamed. Deleting
   needs a decision on sales history and on the gateways bound to the branch, so it is deferred.
2. **No move** of a branch between businesses: every sales row carries the composite key.
3. **Name uniqueness is enforced by the API only.** Older CLI-created duplicates are tolerated, and the CLI does not
   check names. There is no database constraint, because duplicates that already exist would make it fail.
4. **The platform role bypasses RLS.** Its grants keep it to provisioning tables, but within those it can read and
   insert for any tenant. Its actions are audited, the read-only listing included. Some managed PostgreSQL services do
   not allow BYPASSRLS on non-superuser roles; there, a deployment would need a different design (for example
   per-command tenant contexts).
5. **`app_session_memberships` trusts the session id**, which is not a secret to the database itself: an attacker with
   SQL access as `pos_app` can read `user_sessions`. The narrowing removes the trivial enumeration by user id, but does
   not stop an attacker who already has runtime database access.
6. **The rate limit is per IP and per process** (60 mutations/min), not shared across instances.
7. A rename is not propagated to gateways: they keep their local branch name until re-initialized. Reports read the
   cloud name.
